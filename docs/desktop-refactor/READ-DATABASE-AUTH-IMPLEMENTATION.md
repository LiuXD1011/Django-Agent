# Shared read database and authentication

This implements the storage/authentication portion of the approved [Query Worker design](CORE-READ-WORKER-DESIGN.md). Goal II.5 authorizes continuation after this design record; root owns runtime routing, session epochs and integration. No commit, live database, GUI or model access is involved.

The frozen `DatabaseReader` contract provides readonly `path`/`dataRoot`, generic `get`/`all` with the existing `Row` and `BindValue`, and `read(name, id: BindValue)`. `CoreDatabase` satisfies it structurally while retaining its existing write API and immediate transaction semantics. A shared codec handles exact integers, JSON, booleans and approved business table validation; write validation/defaults stay unchanged.

`ReadDatabase(path, dataRoot, {timeoutMs?})` opens only an existing native readonly connection. It neither creates a directory nor initializes migrations, ORM, application, job recovery, credentials or CSRF. It checks existing WAL mode, uses connection-local query-only defense, accepts only native reader/readonly statements, and exposes no native connection or write method. A synchronous `snapshot(work)` uses a deferred transaction and rejects async/thenable callbacks. Queries and authentication in one snapshot see one committed version; the next snapshot sees subsequent commits. No callback, SQL or path becomes a renderer capability.

`AuthReader(database: DatabaseReader, {now?})` owns the single implementation of credential authentication, authoritative revalidation, ACL, safe identity/device projections, session activity and channel authority. `AuthService extends AuthReader` retains its unique owner write methods and original exports/signatures. Protected helpers support those writes without duplicating authentication. Error status/code/message and validation order must remain unchanged.

The separately requested trusted `AuthService.discardIssue(issue)` handles an issued result superseded by a later authentication intent. It uses the owner transaction, does not require now-revoked membership, and does not alter ordinary logout authorization. Device cleanup matches user, device and the issued access digest, so discarding old refresh generation A preserves later generation B in the same stable device family. Legacy cleanup revokes only that user's exact issued access/refresh token pair; transaction failure rolls back both. There is no public route for this helper.

TDD first exercises actual native readonly storage, snapshot consistency and authentication against explicitly incomplete implementations. RED must come from incorrect behavior, not a missing import. Regression fixtures cover exact integers and JSON, read/write rejection, no initialization, nested/error/async snapshot release, full account/API/legacy/channel permissions, disabled/deleted principals and revocations. Relevant existing database/auth/transport tests and core typecheck follow; root runs the unified build to avoid dist races.

The first actual RED has 12 failed checks, including an old/new mixed snapshot, unnormalized native integers and explicit incomplete authentication. Native preparation exposed another concrete boundary: assigning `PRAGMA query_only=OFF` changes connection state during prepare, before `statement.readonly` can reject it. The final wrapper conservatively accepts read starts (`SELECT`/`WITH`/`VALUES`, or their `EXPLAIN` forms) and fixed nonassigning PRAGMAs before preparing, then still requires native `reader` and `readonly`. Comment-prefixed/unknown statements are rejected. The first allowlist's actual queries meet this restriction; no public arbitrary-SQL interface exists. SQLite labels even plain `PRAGMA journal_mode` as potentially writing, so the strict guard rejects it; `SELECT journal_mode FROM pragma_journal_mode` preserves the same read assertion. The constructor separately reads the existing mode and never changes it.

The [first implementation follow-up](../refactor-evidence/20261012-read-auth-first-green.tap) preserves one fixture mistake: trying to write corrupt JSON through the normal owner connection correctly hit its existing CHECK constraint. The repaired fixture temporarily disables that constraint only in its isolated writer, writes the damaged row, restores the constraint and verifies decoding rejects it; this is not additional product RED. Its other failure revealed the genuine prepare-side-effect problem above. The [guard follow-up](../refactor-evidence/20261012-read-auth-guard-green.tap) preserved the strict native rejection of `PRAGMA journal_mode`; changing to its readonly table form retained the same WAL assertion. No permission or data assertions were removed.

Final tests observe the actual native handle's readonly flag and attempt a real native INSERT, which fails with `SQLITE_READONLY`. They also verify unchanged schema versions, metadata, jobs and directory contents through open/read/close; an existing vec virtual table does not require Query-side DDL or extension loading for these page reads. Only actual isolated SQLite fixtures are used. Existing channel tests use controlled loopback HTTP model fixtures, and existing auth tests include password-format interoperability; no external vendor, live configured model or project Django runtime is involved. Command times include test setup and are not page-latency measurements.

The [freeze manifest](../refactor-evidence/20261012-read-auth-freeze.json) binds source/test/evidence hashes, the approved design hash, actual command outcomes, local link/diff checks and temporary script cleanup. Test directories and scripts are removed. No dependency or lockfile changed, and no unrelated source was edited.

This extraction alone does not make a Query Worker or fix live responsiveness. Epoch fencing, allowlist routing, shared cancellation and Windows/live acceptance remain root-owned stages.
