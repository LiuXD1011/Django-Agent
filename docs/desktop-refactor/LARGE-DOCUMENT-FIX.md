# 大文本分块修复计划

**目标：** 修复实际上传 2.88MB、40000 行文本时业务核心持续占用 CPU、健康检查超时的问题。

**架构：** 保留现有 TypeScript 分块算法与解析协议；每次 `splitDocument` 只计算一次全文保护区间，在父块和子块间复用同一组区间。不修改文档正文、偏移单位、保护规则、父子关系、检索范围或模型调用语义。

**技术：** TypeScript、Node.js 22、现有 `node:test` 与 `tsx`。无依赖变更。

## 证据与方案

实际浏览器上传已持久化 14 个文档。大文本处于 `chunking`，核心进程 CPU 单核约 96%，`/health` 五秒超时。离线诊断在第九次全文扫描主动停止：累计扫描 25920000 个字符，原文 2880000 个字符。此诊断上限不是产品成功结果。

选择一次计算、逐层复用，因为原来的 `split` 在每个父块中调用 `ranges(items, source)`，输入始终是完整文档。只扫描父块会改变跨边界保护区间的语义；直接移到工作线程仍会保留重复扫描成本，因此先修复算法。若修复后仍影响健康检查、取消或任务心跳，再处理实际测得的剩余瓶颈。

## 入库与检索的第二个瓶颈

真实页面仅重解析大文本一次，分块完成后停在 `publish_local`。120 秒只读观察记录 33 次三秒健康检查超时。代码与两项 RED 用例确认：`records` 的 SQL 把完整 `d.metadata` 复制到每个子块；12 个片段的小用例即重复传输 12481236 个字符。见 [索引与查询 RED 日志](../refactor-evidence/20261011-root-retrieval-source-scaling-red.tap)。

采用两项内部调整：关键词索引仅加载实际需要的标题和分块；常规检索仍保留完整文档元数据，但每次检索按文档 ID 加载一次并共享，继续检查空间、知识库及启用状态。相比跨调用缓存，这避免过期元数据；相比删减返回字段，保留来源代际和分块策略等原有语义。

## 异常退出后的文档状态协调

当前入库事务无法在十秒内响应正常退出，按精确 PID、启动时间、exe、cwd 和全部参数核验后，仅停止隔离核心进程。事务回滚保留了其余 13 个文档。重启正常队列把任务标为 `interrupted`，但文档仍为 `processing`，两个处理 span 仍为 `running`：应用启动只调用了队列恢复，没有调用已有的文档恢复流程。

启动时由文档恢复流程协调队列及文档审计；没有解析器时仍直接恢复队列。恢复同时处理历史已中断但未协调的记录。只更新当前文档指向的任务状态，不改变正文、来源代际或新的 attempt。已发布内容保留 `completed`，未发布上传显示失败/中断并等待明确重解析；所有手动任务不自动重放。

## 序号冲突检查的索引

第三轮真实大文本仍停在入库，模型用量保持 95 条，没有新增付费调用。只读 `EXPLAIN QUERY PLAN` 确认每个片段的 `seq_id` 冲突检查都执行 `SCAN chunks`；表中仅有 ID、空间/库、父块和媒体父块索引。随着片段增加，这个逐片段检查再次形成平方级工作量。

在 `SearchIndex` 现有的派生结构初始化中增加 `chunks(seq_id)` 非唯一索引，保留既有重复序号检测与 60 位整数语义。不使用唯一约束，以免改变原始迁移数据的准入规则。SQLite 查询计划和真实重复序号用例先 RED，修复后要求实际索引查找且冲突仍被拒绝。
