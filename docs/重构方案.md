# Django-Agent 商用架构审计与分阶段重构方案

> 审计日期：2026-10-02。代码基线：`222383803cf2c6586605b9c5b793afbe3a27b14d`。  
> 本文供 Zcode 分阶段执行；这是经实际测试支撑的重构方案，不是已完成重构的声明。  
> 执行位置：由 Zcode 在实际项目检出目录中自动识别项目根目录，不绑定任何机器、用户名、盘符或 worktree 路径。文内路径按实际项目位置解析；历史测试日志中的绝对路径仅用于审计溯源，不是执行要求。本次审计未修改已有业务源码、用户数据库和生产配置；新增审计脚本、证据与本文。

## 1. 结论与已经确认的产品边界

### 1.1 用户已确认

| 项目 | 目标 |
|---|---|
| 交付顺序 | Windows、Linux、macOS 桌面客户端优先，后续产品化团队私有部署 |
| 数据与部署 | 1000 人共用一个集中式团队后端，不是 1000 个独立本地数据库 |
| 首版负载基准 | 1000 在线，100 路并行生成回答；后者已单独确认 |
| 图谱 | 保留 Neo4j |
| 分发方式 | 开源分发，同时考虑商用服务与交付 |

**最关键的边界：桌面优先不等于本地后端优先。** 1000 人共享数据要求首个承载该规模的版本已经具有集中服务端。可以晚做私有部署安装向导，但不能等到那个阶段才解决共享存储、权限、任务协调和容量。

**判断：项目具备继续产品化的基础，但当前基线不宜直接作为千人团队生产版本。** 原因不是“没有微服务”，而是实测存在授权缺口、索引质量与状态问题、数据库事务中等待模型网络、旧任务执行者仍能改业务数据等问题；当前部署和流式模型也不适合直接横向扩展。

建议目标：

1. **保留 Django 模块化单体**，保留现有 Vue 界面和 Neo4j，不全盘重写。
2. **分离运行角色**：普通 API、真正异步的流式连接、后台 worker、调度/补偿。逻辑分层先于拆微服务。
3. **团队数据底座改为 PostgreSQL + 对象存储**；向量检索优先验证 pgvector，Neo4j 作为可重建图谱投影；Redis 处理共享缓存、限流和通知，不做唯一业务事实源。
4. **先修安全与数据一致性，再迁移基础设施，再做三平台发行与容量认证。** 安装包可以先做原型，但不能绕过发布门禁。

### 1.2 尚待确认，本文不擅自当作事实

- 文档总量、总字节数、平均页数、chunk 数、日新增量、OCR 占比、中英文比例。
- 模型供应商/自部署模型、每次输入输出长度、RPM/TPM 配额、可接受费用。
- 服务器规格、单机或多故障域、运维人员与预算。
- Neo4j 故障是否允许暂时退化到普通混合检索：已发起询问；以下保留两条部署路线。
- 桌面系统最低版本、CPU 架构和必须覆盖的 Linux 发行版；是否要求完全离线安装。
- 团队内的知识库是否需要独立 ACL；是否需要 SSO、审计保留年限及数据驻留要求。

缺少这些数据不影响先做 P0/P1 改造，但影响硬件采购、图谱 HA 选型和最终性能承诺。

## 3. 当前架构：哪些已经有，哪些只是单机能力

| 主题 | 当前实现 | 对商用团队版的意义 |
|---|---|---|
| 主数据库 | SQLite，WAL、30 秒 timeout | 适合本地/轻量部署；不作为本方案多节点团队主库 |
| 缓存 | Django LocMemCache、局部进程缓存 | 不是跨进程/跨主机共享缓存 |
| 异步 | TaskRecord 持久任务、claim/heartbeat/recovery、线程池；聊天另起 daemon thread | 有恢复基础，但未形成独立资源池与端到端防旧写入协议 |
| 流式 | 同步 StreamingHttpResponse、约 100ms 轮询；流状态与事件可落库 | 已有断线续传基础，不能说“全在内存”；连接承载和写放大需重做 |
| 分布式 | 本地文件锁、数据库 CAS、持久任务与流记录 | 同机多进程能力不等于多机整体一致性 |
| 微服务 | Django apps 划分，核心仍在大模块 | 是可演进的单体，不需要为商用先拆十个服务 |
| 向量/全文 | SQLite FTS + sqlite-vec，全局向量状态 | 租户/知识库候选和 embedding 空间存在实测缺陷 |
| 图谱 | Neo4j driver、图提取/搜索/清理 | 保留功能；与主库之间需可靠投影协议及部署健康定义 |
| 安全 | 自定义 bearer/API-key、TenantMember、对象租户过滤、部分管理员校验 | 有隔离基础，但认证与动作授权没有统一封口 |
| 交付 | Vue 生产构建、Waitress 本地启动器、用户数据路径与生命周期测试 | 已有桌面运行基础；不等于三平台签名安装包流水线 |

主配置见 [settings.py](../config/settings.py) 的 121、144、153、271 行附近。桌面线程配置见 [start_desktop.py](../scripts/start_desktop.py) 132–138 行。虽然已有 [asgi.py](../config/asgi.py)，但仅存在 ASGI 入口不代表同步流与后台工作已经异步化。

应保留的成果：租户对象过滤、子表租户一致性回归、自动初始化默认关闭、生产缺失 SECRET_KEY 拒绝启动、跨平台文件锁/用户数据目录、任务 claim/owner 校验、流落库及终态持久化。新增验证中的“跨租户读取返回 404”“陈旧缓存不覆盖数据库任务终态”均通过。

## 4. 问题清单与修复优先级

等级定义：P0 阻断任何多人商用发布；P1 阻断千人团队版；P2 产品化和持续交付必须完成。以下“实测”对应 audit_probes 中同号用例，测试数据均为临时夹具。

### F01 / P0：有租户不等于有写权限

- **实测 01**：viewer 对自己租户内知识库执行 DELETE，实际 `200` 且 `deleted=True`；预期 `403` 且数据不变。
- [view_security.py](../personal_knowledge_base/view_security.py):11 只处理 tenant_required；[knowledge/views.py](../knowledge/views.py):356 附近的管理动作未统一使用角色约束。
- 影响：只读成员可以执行破坏性操作。跨租户过滤通过不能掩盖同租户角色越权。
- 修复：集中权限服务，以 `principal + tenant + action + resource` 判定，默认拒绝；覆写、删除、上传、重建、移动、导出、模型凭据、成员管理分别列动作。API-key 使用带 scope 的 service principal，不默认等同 owner。
- 验收：角色×方法×资源归属矩阵；viewer 只读；跨租户 404/403；所有旧兼容路由同样覆盖。

### F02 / P0：禁用账号的既有 token 仍有效

- **实测 02**：`is_active=False` 后原 bearer 读取知识库仍 `200`。
- [authentication.py](../personal_knowledge_base/authentication.py):30–51 校验 token 过期/撤销，但没有把用户禁用完整纳入认证。
- 修复：用户 active、用户/租户删除状态、租户 active、有效成员身份都进入认证；禁用/移除成员/改密/撤权更新认证版本并撤销相关会话。长连接重新授权/接收撤权通知，不能仅在连接建立时检查一次。
- 额外代码证据：[models.py](../personal_knowledge_base/models.py):61 的 AuthToken 存明文 token，前端将 access/refresh 放 localStorage。增加 token 摘要存储、刷新轮换与重放检测；桌面 refresh 用系统凭据库、access 尽量短期驻内存。这是凭据泄漏面治理，不是本次已经验证 XSS 的声明。

### F03 / P1：全局向量 Top-K 后过滤导致本租户/本知识库漏召回

- **实测 03、04**：全局最近的两个候选来自其他租户或其他知识库，本范围内有效目标排在其后，实际结果 `[]`。
- [search.py](../personal_knowledge_base/search.py):492–520 在 vec0 的 KNN 限额后才做范围过滤。
- 这是召回正确性/可用性缺陷；本次没有证实它直接返回其他租户内容，不把“漏召回”误写成“已泄漏”。
- 修复：索引空间明确 tenant、KB、模型版本，候选生成和 ACL 约束协同设计；小候选集合做精确近邻，较大集合验证分区/ANN 参数与最终过滤。单纯把 K 乘 10 不能保证正确。
- 验收：多租户污染、同租户多 KB、禁用/删除 chunk、稀疏 ACL、大租户挤占；与过滤后精确真值对比 Recall@K。

### F04 / P1：写入、查询、重建没有共享 embedding 空间契约

- **实测 05**：索引使用 `document-model-A`，查询使用空 model_id（默认模型），实际调用参数 `['document-model-A', '']`。
- [search.py](../personal_knowledge_base/search.py):185、496、1114；[model_providers.py](../personal_knowledge_base/model_providers.py):1043 的签名也不是完整模型版本标识。
- 同维度不等于同语义空间；跨 endpoint/模型版本混用会产生看似正常的错误相似度。
- 修复：持久化 embedding_space_id，包含 provider、endpoint 标识、model/revision、dimension、归一化/距离、预处理版本；不包含密钥明文。按空间查询并在结果层融合，禁止跨空间直接比较距离。
- 全局 vec 表按维度重建路径还会影响全部数据，应改为影子 namespace 而非请求中 drop 当前索引。

### F05 / P1：部分重建失败仍报告 ready

- **实测 06**：`indexed=1, errors=1, batches=2, cancelled=False`，索引元数据仍 `status='ready'`。
- 修复：构建新 generation，记录 expected/indexed/failed/skipped、checkpoint 和失败对象；达到明确完整性规则才切换 active generation。错误、取消、超时均保留旧可用版本。
- 验收：第二批故障、维度改变、取消、重启、同时编辑文档；旧索引可查，新索引不冒充完整。

### F06 / P0：不完整/非权威事件用于破坏性重建消息

- **实测 07**：删除旧 Message 后注入新建失败，`original_exists=False`。
- **实测 08**：只有不完整事件序列时，已有完整回答被替换为 `content='' completed=False`。
- [event_log.py](../personal_knowledge_base/event_log.py):118 明确轨迹追加失败可返回 None；571–596 重建先删后建且没有整轮原子事务。
- **不要把目前轨迹系统称为完整 Event Sourcing。** 本方案近期保留 Message/Turn 为业务事实源，轨迹为观察资料；重建只针对经验证完整的版本，采用影子投影与短事务切换，失败保留原记录。
- 如果未来真采用事件溯源，必须另立 ADR，保证事件与业务写同事务、严格版本与迁移、完整事件载荷及重放验证，不能只改函数名。

### F07 / P1：事务内模型网络调用占用 SQLite 写能力

- **实测 09**：实际更新 chunk 进入模型 HTTP 时，另一个连接更新无关 Tenant，返回 `database is locked`（探针等待 0.25 秒）。它证明持锁跨 HTTP，而非声称生产 30 秒一定耗尽。
- [chunk_mutations.py](../personal_knowledge_base/chunk_mutations.py):218–231；[knowledge/views.py](../knowledge/views.py):749–787 还在事务内触发索引/图谱工作。
- 修复：短事务只改文档版本和 outbox；网络计算在事务外；最终发布时条件更新版本。不能仅增加 busy_timeout 或改为 PostgreSQL 后继续长事务。
- SQLite WAL 允许读写重叠但仍只有一个 writer，且不适用多主机共享 WAL 文件；因此本方案不采用共享盘挂同一 SQLite 做 HA。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html)

### F08 / P0：任务租约保护了状态，不足以保护业务写

- **实测 13**：处理中 task owner 被接管成 `new-owner`，旧执行者仍删除原 chunk 并将文档标为 completed；实际 `{'task_owner':'new-owner','original_chunk_exists':False,'document_status':'completed'}`。
- [tasks.py](../personal_knowledge_base/tasks.py):217、402 附近已有 claim/heartbeat；但执行函数与 [document_processing.py](../personal_knowledge_base/document_processing.py):402、421、467 的业务修改没有共享 fencing 条件。
- 修复：任务租约+单调 fencing_token+文档 expected_revision；每个发布事务校验三者。新 chunks/文件/graph generation 先写 staging，旧 worker 只允许产生可清理临时产物，失去所有权后禁止切换有效版本。
- 验收：解析中接管、向量中接管、图谱中接管、取消后旧进程恢复、租约过期再重试，均不能修改新版本。

### F09 / P1：同步长连接与有限线程竞争

- **实测 15**：4 条测试同步 SSE 占满 Waitress 的 4 个线程，真实 `/health` 在约 0.609 秒时超时；释放流后返回 200。
- [chat_runtime.py](../personal_knowledge_base/chat_runtime.py):63 每次任务建 daemon thread；[chat/views.py](../chat/views.py):1244、1279、1586 附近同步轮询。
- 桌面启动器是本地用途，不能将该结果外推成“所有 Django 部署最多 4 人”。但原样把此入口当团队服务器明显不匹配负载。
- 修复：真正 async SSE 迭代器+异步等待通知、生成独立受控 worker、API/stream 资源隔离、连接与生成分别配额。仅把启动命令换 ASGI 而不处理同步阻塞，不算完成。[Django StreamingHttpResponse](https://docs.djangoproject.com/en/5.2/ref/request-response/#django.http.StreamingHttpResponse)

### F10 / P1：健康端点只是 liveness，不是发布 readiness

- **实测 10**：`/health -> 200 {'status':'ok'}`，不存在 ready/components。它是所需运维能力的缺口，不是现有“活着”语义本身错误。
- [views.py](../personal_knowledge_base/views.py):416。
- 分离 `/livez`、`/readyz`、受控 `/health/components`。活性不深查 DB/模型，避免依赖故障触发重启风暴；readiness 有时间预算并报告 DB、迁移版本、共享存储能力、worker 延迟等。
- 图谱是否令全系统 unready 取决于业务降级约定；不要 Neo4j 一断全 API 全部摘除，也不要图功能失效仍对外宣称完整健康。

### F11 / P1：配置看似可调，实际没有接入

- **实测 14**：子进程设 workers=9、SQLite timeout=7、TPM=4321，读取设置仍 `{'workers':4,'sqlite_timeout':30,'tpm':None}`。
- 指的是探针对应配置未接环境变量，不是说全项目不支持 `.env`。
- [settings.py](../config/settings.py):121、271；[model_rate_limit.py](../personal_knowledge_base/model_rate_limit.py):41 默认 120000，文件锁与等待循环缺少统一截止时间。
- 修复：类型化配置、合法范围、启动校验、脱敏 effective-config、环境变量测试；团队模式不存在的依赖应启动失败，不静默回本地 SQLite/LocMem。

### F12 / P1：主库、索引、Neo4j、文件系统缺少统一可靠变更协议

- **代码证据**：[chunk_mutations.py](../personal_knowledge_base/chunk_mutations.py):140–152 的 after-commit 图清理失败只记录日志；主库提交后进程崩溃或外部调用失败，缺少与该提交绑定的耐久重试。
- 部分知识库清理已有补偿/重试测试，不能笼统说“全项目没有补偿”；问题是常规变更协议未统一。
- 修复：事务 outbox、投影 consumer 幂等、删除 tombstone、对象引用计数/延迟清理、全量校对任务。Neo4j 已有命名空间及部分租户过滤，继续保留并扩大实际服务端集成覆盖。

### F13 / P1：进程内缓存与本地文件锁不能直接承担团队协调

- **代码证据**：LocMemCache；模型限流 FileLock；AppConfig.ready 启动线程与恢复器。Django 官方明确本地内存缓存属于进程私有。[Django cache](https://docs.djangoproject.com/en/5.2/topics/cache/)
- 新开一个 API 副本会带来新的本地缓存/资源竞争；部署、迁移、管理命令不应通过 argv 猜测启动后台组件。
- 修复：API 无后台副作用；显式 worker/scheduler 入口；共享配额原子操作；缓存状态不当事实源。已有 DB 任务终态优先逻辑必须保留。

### F14 / P2：模块边界、依赖和发行工程不足

- **代码证据**：tasks.py 2112 行，chat/views.py 1701 行，personal_knowledge_base/views.py 3107 行，model_providers.py 1429 行。行数不是缺陷本身，但跨鉴权、网络调用、投影、事务、UI 兼容耦合已经体现在上述问题。
- 后端 requirements 多项只约束下限；一次全新安装即可复现 exporter 私有 API 不匹配。前端有 lockfile，不应误说“所有依赖没锁”。
- **实测**：冷缓存启动依赖 tokenizer 下载；前端构建通过但主包偏大。已有路由懒加载，继续基于 bundle 分析拆重依赖，不只是机械添加懒加载。
- 本仓库没有可核验的三平台签名安装包发行流程；Langfuse Compose 文件不是主业务多节点部署方案。
- 修复：锁完整传递依赖与哈希、按 API/worker/eval/desktop 分依赖组、打包离线资源、平台构建测试、SBOM/许可证清单、升级协议与回退。

## 5. 目标架构与模式选择

```text
Windows / Linux / macOS 薄客户端（Vue + 桌面壳；保留 Web 接入）
          │ HTTPS：版本握手、认证、普通 API、SSE、上传下载
          ▼
TLS 入口 / 限制请求体 / 路由 / 限流 / 访问日志
          ├── Django API 副本 A、B（无本地业务状态）
          └── Async SSE 副本 A、B（无粘性依赖，可重连）
                         │
     PostgreSQL：业务事实 + task + outbox + stream checkpoint
          │        │                │
          │        └── Redis：共享缓存、配额、唤醒通知（可重建）
          └── 独立 Worker 池：chat / ingest / graph / maintenance
                    ├── 模型 Provider Adapter（限流、截止时间、熔断）
                    ├── 对象存储（原文、解析产物、附件）
                    ├── Search Adapter（pgvector + 经验证全文方案）
                    └── Neo4j（图谱投影、可追踪 generation）
          监控 / traces / 审计 / 备份 / 恢复演练贯穿各组件
```

多个进程并不等于多套领域代码。先共用一个仓库、一套版本、一套应用服务，以不同入口/队列分资源；仅在独立扩容、故障隔离或团队协作收益有证据时再拆服务。

| 模式 | 用在本项目哪里 | 刻意不做什么 |
|---|---|---|
| Strangler / Anti-Corruption Layer | 保留旧 API，逐个路由转向新服务层/存储适配器 | 一次替换所有模块 |
| Async Request-Reply / Queue-Based Load Leveling | 上传/重建返回 task_id；队列吸收峰值 | HTTP 请求内完成文档全流水线 |
| Competing Consumers + fencing | 多 worker 领取任务，所有发布写检查租约与版本 | 把“有队列”误当 exactly-once |
| Transactional Outbox / Materialized View | PostgreSQL 提交事实和待投影事件，Neo4j/检索异步更新 | DB 与图谱之间伪造全局事务 |
| Bulkhead | API、长连接、聊天、解析、图谱、评估分池 | 评估/OCR 挤占在线回答资源 |
| Cache-Aside | tenant/权限/数据版本约束的查询结果缓存 | 缓存永久决定授权、任务终态 |
| Circuit Breaker + bounded retry | 模型、Neo4j、对象存储各自预算 | 多层无限重试、占着事务等恢复 |
| Health Endpoint Monitoring | 活性、就绪、组件能力各有语义 | 单一 `{status:ok}` 代表全部可用 |

模式依据与适用性参考 [Competing Consumers](https://learn.microsoft.com/en-us/azure/architecture/patterns/competing-consumers)、[Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)、[Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)。表中落地选择是针对本仓库问题的设计判断，不是模式文档证明已达到某吞吐量。

## 6. 数据、检索和 Neo4j 改造细则

### 6.1 PostgreSQL 不是仅改 DATABASE_URL

1. 审计 migrations、sqlite-vec extension、FTS SQL、PRAGMA、INSERT OR IGNORE、last row id 等 SQLite 耦合，移入适配器。
2. 先引入后端接口并保留现有 SQLite 适配实现；团队模式运行 PostgreSQL，开发/迁移工具才保留 SQLite。首版不额外承诺离线桌面同步。
3. tenant_id 覆盖所有业务表/唯一约束/必要联合索引；避免只按资源 UUID 查后再补授权。可加 PostgreSQL RLS 作纵深保护，但需验证事务连接上下文和后台管理员路径，不能直接全局开启了事。
4. 导入脚本有 dry-run、checkpoint、版本清单、行数/外键校验、附件 SHA256、抽样内容比较。UUID 保留，序列复位，统一时区、JSON 与空值语义。
5. 第一轮迁移采用停写窗口：停止任务领取→等待/取消在途任务→一致备份→导入→核对→只读验收→切换→再开放写。避免一开始做高风险 SQLite/PG 双写。
6. 数据库连接池设总体预算：API/worker/stream 总连接数留管理余量；SSE 等待不得长期占有事务或连接。

### 6.2 新实体/约束（建议设计，尚未实现）

| 实体 | 关键字段/约束 |
|---|---|
| DocumentRevision | tenant_id, knowledge_id, revision, content_hash, state；同文档 revision 唯一 |
| Task | tenant_id, type, resource_id, expected_revision, idempotency_key, lease_owner, lease_until, fence, attempt, deadline, next_retry_at |
| Outbox | event_id 唯一，aggregate_id, aggregate_revision, schema_version, payload/ref, created_at, delivered_at |
| ProjectionCheckpoint | consumer, aggregate_id, last_revision；重复/过期版本不重复应用 |
| EmbeddingSpace | provider/endpoint 指纹、模型 revision、dim、distance、normalization、preprocess_version |
| IndexGeneration | tenant_id, kb_id, space_id, generation, expected_count, indexed_count, failed_count, state, active_since |
| StreamCheckpoint | tenant_id, user/session/message_id, generation, last_seq, final_state, expires_at |
| ServiceCredential | token_prefix、token_digest、scopes、tenant、expires_at、revoked_at；不存可回放明文 token |

这些表不要求一次全部上线。先扩展兼容字段和约束，再后台回填，再切读写，最后下一版本收缩旧字段。

### 6.3 搜索 Adapter 与质量门禁

- 接口至少有 `upsert_generation / delete_document / search / activate_generation / check_integrity`，输入必须带 tenant、可访问 KB 集、embedding_space、corpus_revision。
- 默认候选方向为 PostgreSQL+pgvector，减少额外系统；**换成 pgvector 不会自动修复过滤召回**。官方说明 ANN 扫描过滤可能不足 K，需迭代扫描、分区或精确查询策略。[pgvector 官方文档](https://github.com/pgvector/pgvector)
- 本项目中文 RAG 不能把 SQLite FTS 机械替换成 PostgreSQL 默认词法后直接验收。建立中文术语、编号、混合语言、长短问句测试集；比较应用侧分词+PG 全文与独立搜索引擎方案。仅在质量/规模实测需要时引入 OpenSearch/Qdrant 等额外服务，避免同时迁移三套搜索系统。
- 设精确检索 oracle：小数据全量过滤后算距离，大数据抽样真值。授权过滤必须始终正确；Recall@10 初始建议 ≥0.95，业务检索命中率不得低于修复后的基线，阈值需要数据集确认。
- 向量重建按 generation 构建，期间记录文档增量；构建 snapshot + 增量补齐后原子激活。失败时回到旧 generation，不把部分失败标 ready。
- 嵌入缓存 key 加 space_id/content_hash/租户授权域；原文相同但密级不同，不默认跨租户共享缓存。

### 6.4 Neo4j 必须保留，但明确其角色

- PostgreSQL 保存文档事实、版本及必要可重建图谱输入；Neo4j 保存实体关系投影。**若存在人工编辑的独有图数据，先落事实表/变更日志，不能把它当可丢弃缓存。**
- outbox 触发 graph worker：提取→校验→生成 staging graph→确认当前 fence/revision→切 graph generation。写入唯一键包含 tenant、KB、文档版本、实体 key；重复事件幂等。
- 删除事件带版本 tombstone；旧 ingest/旧消息不得复活已删除文档。定期对账主库版本与图谱版本，输出 lag、missing、orphan 计数。
- Neo4j 网络操作不在主库事务里；超时、熔断、有限重试、死信可运维重放；前端展示 `graph_pending / graph_ready / graph_degraded`，而不是整个知识库笼统 completed。
- 实际 Neo4j 集成必须测试跨租户、跨 KB、重新提取、删除、重复事件、实体重名、关系方向、旧 generation 回滚和备份恢复；现有 mock 测试不替代这些。

**部署路线需产品确认：**

| 路线 | 行为 | 代价与验收 |
|---|---|---|
| 开源精简部署 | Neo4j 单实例+定期备份；故障时图增强降级，混合检索继续 | 不宣称图谱持续 HA；演练恢复和重新投影时长 |
| 图谱持续可用 | 选择具备集群能力的发行版本/服务，跨故障域副本 | 官方集群文档标为 Enterprise；典型容忍一个 primary 故障需要三 primary，不把 Community 单节点包装成 HA |

版本、许可、备份能力与 driver 兼容性在发布前固定验证，不能只看 Python neo4j 包版本。以上集群能力依据 [Neo4j clustering introduction](https://neo4j.com/docs/operations-manual/current/clustering/introduction/)。

## 7. 异步任务、缓存、限流和流式服务的具体设置

### 7.1 先完成耐久任务协议，再决定是否需要消息中间件

首轮推荐 **PostgreSQL task/outbox 为事实源，专用 worker 用受限轮询和 `FOR UPDATE SKIP LOCKED` 领取**，Redis 只做唤醒。现有 TaskRecord 迁移成本较低。若后续有跨语言消费/巨大消息量，再接成熟队列；broker 仍不能代替业务幂等与 fencing。

事务与业务步骤必须是：

```text
T1：认证授权 -> 建 revision -> 建 task + outbox -> COMMIT -> 返回 202/task_id
T2：短事务领取 task -> fence 递增/设置 lease -> COMMIT
事务外：解析 / 调模型 / 写 staging artifact / 生成图谱候选
T3：检查 owner + fence + lease + expected_revision + cancellation
    -> 仅当全部匹配，发布新 revision/索引指针和 outbox -> COMMIT
消费者：应用已提交事件 -> 记录 checkpoint -> 重复消息返回已有结果
```

- 租约时间依据阶段耗时设置；建议起点 heartbeat 10 秒、lease 60 秒，仅作为压测前配置，不是所有任务固定值。
- 任务 deadline、每次调用 timeout、总 retry budget 分开配置；指数退避+随机抖动，尊重 Retry-After。解析失败和非法输入不无意义重试。
- 幂等键包括 tenant、动作、resource、revision；再按请求 ID 防止前端重复提交。队列语义为至少一次，业务效果由约束和版本发布达成幂等。
- 对同文档冲突写进行序列化，不把所有租户串在一个全局锁上。
- chat / ingest / graph / maintenance 分队列配额；eval 不参与默认在线 worker。慢租户采用公平调度、并发/存储/token 预算。
- 杀死 worker、租约过期、重放、取消是必测正常运行场景，不靠 finally 假设一定执行。

### 7.2 缓存：按性质分，而不是到处加 Redis

| 数据 | 策略 | 失效/故障处理 |
|---|---|---|
| 模型元配置 | 短 TTL + config_revision key；缓存脱敏字段 | 修改发布失效事件；密钥留凭据服务 |
| 检索结果 | tenant + ACL version + KB 集 hash + query hash + corpus_revision + space_id | 文档/权限版本变更立即换 key，TTL 作兜底 |
| embedding | content_hash + space_id + 授权域 | 模型/切分版本切换自动隔离 |
| task 状态 | 短期展示缓存 | 数据库为准；终态不可被旧缓存逆转 |
| 权限/撤权 | 以权威状态检查为主，版本号传播 | 失效不确定时拒绝敏感动作，不放行旧权限 |
| stream 唤醒 | Redis 通知，支持丢通知后补拉 | 通知不是唯一事件存储 |

建议起点：元数据 TTL 30–60 秒，检索缓存 30–120 秒并带 ±20% 抖动；具体由命中率和一致性预算调整。对热 key 用请求合并、限时重建锁，负缓存 5–10 秒；锁必须有 owner token 和过期，释放时比对 owner，不能无条件 DEL 别人的锁。

Redis 故障：普通缓存可限流后回源；配额服务失效时昂贵生成按保守策略排队/拒绝，不能无限放行；已有 stream 可按 checkpoint 有界补拉。禁止把 Redis 丢数据变成业务终态丢失。

### 7.3 模型配额与外部依赖

- 配额维度至少包含 provider account、模型、租户、用户/服务凭据、任务种类；相同模型名不等于相同供应商配额池。
- 同时限制并发数、RPM、TPM、队列长度/等待时长；先预留预计 token，结束按实际用量结算，失败/断连释放预留；拒绝应有明确错误码与 Retry-After。
- 所有 chat、stream、embedding、rerank、summary、graph、eval 路径统一走 provider adapter；不留下绕过配额的“辅助请求”。
- 日志记录配置版本和 provider request id，不记录密钥/完整文档；为模型超时、429、费用异常设告警。
- 只有幂等且尚未向用户输出的阶段才自动切换供应商；已经输出部分答案后不能悄悄拼接另一模型的回答。

### 7.4 SSE 与消息持久化

- Web API 接受生成请求后返回 message_id/task_id；生成在有配额的 worker；SSE 仅订阅，用户关闭窗口不应意外破坏已确认提交的任务。
- 单独 async SSE 入口，检查从中间件到 generator 均不存在同步长阻塞；同步 ORM/解析工作移出事件循环。不能用每连接一条后台线程来冒充异步。
- PostgreSQL 保留可恢复序号/批次和消息终态；Redis 用于低延迟 fan-out。建议先按 50–100ms 或累计一定字节批量持久化，平衡写放大与可恢复窗口；业务定义允许的窗口后再确定值。
- 客户端带 Last-Event-ID 或显式 cursor 重连，服务端验证 tenant/user/session 所属，重复 seq 幂等处理，缺口走快照+后续事件；过期 cursor 返回明确重同步状态。
- 完整消息终态必须先耐久提交，再发送成功完成事件；内容、usage、引用、终态版本一致。没有持久化成功就不能给出“已保存”。
- 控制每用户连接上限、心跳、代理 idle timeout、最大排队字节；慢消费者断开后可续传，不能拖住全局生产者。
- 事件保留基于终态时间与合规策略；不要仅依据流创建时间清理仍活跃的流。保留时间不足时提供最终消息快照。

| 连接 | `DATABASE_URL`, `REDIS_URL`, `OBJECT_STORAGE_*`, `NEO4J_*` | 启动检查、secret 引用、连接池/超时预算 |
| 任务 | `TASK_POOL_*`, `TASK_LEASE_SECONDS`, `TASK_HEARTBEAT_SECONDS`, `TASK_MAX_ATTEMPTS` | 类型/上下界；不接受负数或无限值 |
| 流 | `STREAM_MAX_CONNECTIONS`, `STREAM_USER_LIMIT`, `STREAM_RETENTION_SECONDS` | 多副本统一上限与本机资源上限分别管理 |
| 模型 | provider-specific RPM/TPM/concurrency/deadline | 不仅一个全局 `MODEL_RATE_LIMIT_TPM` |
| 发布 | `APP_VERSION`, `SCHEMA_VERSION`, `API_COMPAT_MIN/MAX` | 客户端握手、滚动升级校验 |
| 安全 | host/CORS/可信代理/TLS/cookie/SSO 设置 | 不使用 debug 默认值部署；脱敏输出生效配置 |

现有 `DJANGO_DEBUG=false`、`DJANGO_SECRET_KEY`、`DJANGO_ALLOWED_HOSTS`、`ALLOW_AUTO_SETUP=false` 继续保留。团队配置运行 `check --deploy`，逐项处理警告；TLS 终止代理只信任明确来源，不能无条件信任用户传来的转发头。[Django 部署检查表](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)

### 8.2 商用安全基线

- 统一认证/授权中间层与服务层二次资源校验；所有新旧 API 纳入路由清单；download/export/graph/task/stream 不能成为旁路。
- 密钥通过部署 secret 管理、最小权限数据库账号、轮换与审计；禁止客户端持有模型/Neo4j/对象存储管理员密钥。
- 桌面固定受信前端资源，不给任意远端页面开放原生文件/命令能力；模型生成 HTML/Markdown 清洗，链接外跳和文件下载单独校验。
- 上传先隔离：限制总大小、解压比、文件数/页数、像素、CPU/内存/时限；解析子进程无网络/最小权限；按实际内容而非扩展名校验。复用已有路径/权限防护，并补恶意压缩包/解析器超时测试。
- URL 抓取防 SSRF：规范化 URL、允许协议/域名策略、DNS/IP 与重定向逐跳检查，阻止私网/元数据端点；模型可调用工具按用户授权白名单执行，检索到的文档指令不等于执行权限。
- 审计记录 actor、tenant、action、resource、result、request_id、时间，不记录密码/token/全文；管理员操作与数据导出必须可追踪。
- API key scope、速率、撤销、到期完整覆盖；团队邀请与首管理员 bootstrap 用一次性受控机制，不在安装时自动创建通用管理员口令。
- 日志/traces/评估数据的外送须可关闭、可配置驻留；用户删除传播到原文、向量、图谱、缓存、导出副本，并说明备份保留策略。

### 8.3 HA 与恢复不是“起两个容器”

初始建议 SLO 供确认：普通 API 月可用性 99.9%；已确认提交的核心消息/文档事实在单进程故障下不丢失；备份恢复目标暂定 RPO ≤15 分钟、RTO ≤60 分钟。后两项是待演练的目标，非当前保证；同步复制确认范围与跨故障域备份的 RPO 分开定义。

- API/stream 至少两个副本；负载均衡入口本身需冗余；停止接收新任务、drain 长连接、有界关闭。
- PostgreSQL 选择受支持的主备/故障转移机制，明确同步/异步复制取舍；模拟主库故障、只读、连接池耗尽，验证写入结果不歧义。
- Redis HA 与持久化策略按职责设计；通知丢失可补拉，配额恢复避免瞬时超发。
- 对象存储有持久性、版本/删除策略和校验；本地磁盘只作临时目录，副本换节点仍能拿到同一附件。
- Neo4j 按第 6.4 节路线定义图谱可用性；单机版本与 HA 版明确不同标签。
- 备份至少包含 PostgreSQL、对象清单/内容、加密密钥恢复流程、Neo4j 备份或重建所需事实、schema/模型/索引版本。存到独立故障域并定期真实恢复。
- 监控指标：API P95/P99、错误率、active streams、event-loop lag、线程/内存、数据库池等待/锁等待、queue age、重试/死信、lease 丢失、outbox lag、graph/index lag、token 消耗与上游 429。
- trace/span 关联 request_id/task_id/revision；不得将原始 user/query 作为无界 metric label。Langfuse 可选，监控故障不应阻塞主业务。

## 9. 1000 在线 / 100 并行生成：容量与验收

### 9.1 明确计量，避免伪千人测试

1000 个 token/注册账户不等于 1000 在线；1000 个空闲连接也不等于 1000 个生成任务。测试报告必须分别列出 logged-in clients、active SSE、active generations、API RPS、入库速率、队列等待和上游配额。

一个**用于规划的例子**：平均每路生成持续 30 秒，100 路并行意味着稳定完成速率约 `100/30 = 3.33 turns/s = 200 turns/min`。若每轮输入 4000、输出 1000 token，则总量约 `200 × 5000 = 1,000,000 token/min`，还没计入 rerank、图谱、重试等。此数字是明示假设下的算式，不是实际 provider 配额；不同供应商分别计算输入/输出等限额。

若未来要求 1000 路并行且其余假设相同，对应约 2000 turns/min、1000 万 token/min；不是桌面安装包优化能解决的事情。

### 9.2 压测程序与数据矩阵

1. 在独立负载机建立受控模型 stub，支持固定 TTFT、流速、响应长度、429/5xx/超时/中途断流。**stub 结果只证明平台，不代表真实模型容量。**
2. 构造至少：单团队1000用户；多租户含一个大租户；同租户多KB与稀疏ACL；1万/10万/100万 chunks 三档（是假设测试档位，不是当前用户实际规模）。
3. 负载梯度 1→10→50→100→500→1000 在线，活跃生成上限随梯度到100；每阶段记录升温、稳态、退出，资源异常则停止升压。
4. 参考组合：100 路生成、其余用户带思考时间访问列表/检索/历史；同时持续上传/解析、10%流重连、少量删除/改权限。正常 API 目标负载先以可配置100 RPS做起点，不把它当用户已承诺值。
5. 最后一档稳态至少60分钟、长稳态8小时；完整测试不能只持续数秒。
6. 第二阶段接真实付费/自建模型，在确认配额与预算后逐级放量，分别报告 TTFT、生成速率、端到端质量、429 和费用。
7. 失效演练：杀 API、杀生成 worker、Redis 中断、PG failover、Neo4j 不可达、对象存储超时、丢通知、断网重连、滚动升级；验证恢复后数据/授权/终态一致。

### 9.3 首轮建议验收阈值（待真实硬件校准）

| 指标 | 建议门槛 |
|---|---|
| 授权 | 任意已知越权/跨租户内容泄露为0容忍；撤权行为有端到端测试 |
| 普通短 API | 目标负载内 P95 ≤300ms、P99 ≤1s；明确接口集合，不含模型生成 |
| 检索 | 指定数据规模下 P95 ≤1s；同时满足召回质量与ACL正确性 |
| SSE | 服务端收到上游片段到客户端可读的附加延迟 P95 ≤250ms；单独报告公网影响 |
| 承载 | 1000已登录用户、100并行生成持续60min；错误率<0.5%，主动限流单独计数 |
| 资源 | 内存长稳态无持续增长；连接池/线程有界；峰值留至少约30%余量并记录依据 |
| 队列 | 目标吞吐下最老任务等待不持续发散；超预算请求显式排队/拒绝 |
| 耐久性 | 已确认终态跨进程故障保持；重复提交/投递不产生重复业务效果 |
| 恢复 | 达到确认后的RPO/RTO；实际恢复并核对，不仅备份命令成功 |

不要现在凭用户数承诺固定“几核几G”。先用一个明确记录规格的压测环境测服务曲线，再做冗余与容量预算；若模型自托管，GPU资源另算。

## 10. 三平台桌面安装包方案

### 10.1 建议：Vue + 薄桌面壳，连接统一后端

推荐先验证 Tauri 方案；若团队 Rust/WebView 维护成本高，做 Electron 对照小样后形成 ADR。不要同时维护两种壳。Tauri 的分发支持各平台安装形式，但签名、公证、依赖和测试必须分别实施。[Tauri 官方分发说明](https://tauri.app/distribute/)

- 桌面端保存后端 HTTPS 地址/组织信息，登录后请求能力与版本；集中式模式不启动 Python/SQLite/Neo4j/Docker。
- 保留现有本地 Waitress 入口用于开发/历史单机用户，不冒称它就是团队桌面版；未来若要离线模式，另做数据同步与冲突方案。
- 网络统一经过 endpoint resolver：axios、fetch SSE、上传、下载、图片、登录刷新均使用相同地址和鉴权策略。当前 [client.ts](../frontend/src/api/client.ts) `baseURL=''` 与 [index.ts](../frontend/src/api/index.ts) 的直接 fetch 都要处理，不能只改 axios。
- 跨来源部署精确配置 origin、TLS、CORS、cookie/CSRF 或 bearer；不得为解决连接问题全局 `*` 放开授权来源或关闭证书校验。
- refresh token 使用 Windows Credential Manager / macOS Keychain / Linux Secret Service 等系统凭据存储；选择受支持组件并验证锁屏/不可用/多账户/卸载行为。前端 JS 不获得任意主机文件访问能力。
- UI 能明确区分后端离线、登录过期、版本不兼容、排队、模型配额不足、图谱降级。

### 10.2 构建与发布矩阵

| 平台 | 首选产物 | 必测 |
|---|---|---|
| Windows | 签名 `.msi` 或安装 `.exe` | 普通用户安装、中文/空格路径、无开发环境、升级/卸载、凭据保护 |
| macOS | 签名与公证 `.dmg`/`.app` | Apple Silicon/Intel 支持声明、Gatekeeper、钥匙串、代理/企业证书 |
| Linux | `.AppImage` + 选定发行版 `.deb`（按需求决定更多） | 声明发行版与glibc/WebView依赖、桌面入口、Secret Service、更新 |

采用对应 OS 的 CI runner 构建并在干净机器安装；不把一个 Windows 构建等价于三平台可用。签名密钥不进仓库，发布产物包含 checksum、版本、签名、SBOM、许可证说明。

更新必须：验证签名→下载到 staging→确认 API/schema 兼容→原子替换→失败恢复旧客户端。服务端支持至少上一稳定客户端版本的窗口；大版本迁移有提示与可控升级渠道，企业支持关闭自动更新。

若未来发行本地完整后端包，再单独解决 Python/原生库、sqlite-vec、tokenizer、解析器、可选 Neo4j 及离线许可证；本次实际冷启动下载失败已经说明简单压缩源码不足以交付离线安装。

### 10.3 开源商用与依赖清单

开源可以商用，但项目自身 LICENSE 不能代替全部第三方义务。当前仓库采用 MIT 文本，依赖包含 PyMuPDF/Artifex 组件；官方提供 AGPL/商业许可路径。开源分发并不自动完成兼容性与分发义务，需要明确最终发布许可证、提供对应源码/通知、固定组件版本与分发方式。[Artifex licensing](https://artifex.com/licensing)

发布门禁：生成 Python/npm/OS 镜像/桌面壳/解析器/Neo4j 的 SBOM、许可证清单与 NOTICE；对实际打入安装包和服务端镜像的组件逐项确认。若选择不同许可路线，记录依赖替换或授权决策。此处不把某个库简单等同于“不可商用”。

## 12. 发布、迁移与回退总门禁

### 12.1 每次部署前

- [ ] 保留当前版本镜像/安装包、schema版本、配置指纹与可恢复备份；密钥不进入报告。
- [ ] 数据migration采用 expand→backfill→switch→contract；至少一个兼容发布周期后才删除旧结构。
- [ ] 全量角色/租户矩阵和关键新探针通过；现有回归失败有闭环，不只统计“跑了多少项”。
- [ ] 候选索引/图谱 generation完整，失败记录有处置，不误报ready。
- [ ] worker协议与API/schema兼容；旧worker退出确认后才启用不兼容新协议。
- [ ] 客户端上一版本兼容，TLS/证书/企业代理/升级签名验证完成。
- [ ] 真实后端负载与故障报告达标；stub与真实模型结果分开。
- [ ] 备份在新环境恢复成功，核对原文、消息、权限、索引版本与图谱；记录耗时。

### 12.2 灰度策略

先内部用户→小租户→指定比例用户→目标负载；按tenant或明确feature flag路由，不随机将同一文档写到不兼容处理器。每阶段比较错误率、P95、queue age、授权拒绝异常、index/graph lag、每轮token费用；数据正确性问题立即停止放量。

### 12.3 回退原则

回退包含软件、schema、业务事件、对象和索引版本，不能等同 `git checkout`。禁止在接受新写之后盲目恢复旧快照；先定义新写回放/兼容路线。对P0权限漏洞使用停写或前向修复，不回退到漏洞版本；对检索/图谱可回active generation。任何破坏性清理先dry-run、备份、人工确认与有界批次，且只操作项目明确的数据范围。

## 14. 最终判断

近期最值得投入的不是“全面微服务化”，而是**动作授权、认证撤销、版本化数据发布、任务fencing、正确的检索空间、可靠异步投影和真实异步流**。完成这些后，数据库、部署和桌面发行才有稳定边界；最后用目标数据、真实依赖和明确SLO证明千人团队容量。

本次已经完成分析、实际复现和可执行方案；尚未实施上述业务重构，也尚未通过千人容量、Neo4j集群或三平台安装认证。
